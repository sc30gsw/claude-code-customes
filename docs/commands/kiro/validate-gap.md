# Kiro Validate Gap Command

## 概要

要件と既存コードベース間の実装ギャップを分析するコマンド。設計フェーズに向けて、実装アプローチのオプションと技術的なリサーチ要件を特定します。

## 基本情報

| 項目 | 値 |
|------|-----|
| コマンド | `/kiro:validate-gap` |
| 引数 | `<feature-name> [analysis-target]` |
| 用途 | 実装ギャップの分析 |
| 許可ツール | Bash, Glob, Grep, Read, Task |

## 前提条件

- 要件ドキュメントが存在: `.kiro/specs/<feature>/requirements.md`
- 存在しない場合: `/kiro:spec-requirements <feature>`を先に実行

## 分析プロセス

### 1. 現状調査

#### 既存コードベース分析
- フィーチャードメインに関連するファイルとモジュールの特定
- 現在のアーキテクチャパターン、規約、技術スタックの使用状況マッピング
- 既存のサービス、ユーティリティ、再利用可能なコンポーネントの文書化
- 現在のデータモデル、API、統合パターンの理解

#### コード構造評価
- ファイル構成、命名規則、アーキテクチャレイヤーの文書化
- インポート/エクスポートパターンとモジュール依存構造の抽出
- 既存のテストパターン（ファイル配置、フレームワーク、モッキングアプローチ）の特定
- 現在使用されているAPIクライアント、データベース、認証実装アプローチのマッピング
- 確立されたコーディング標準と開発プラクティスの記録

### 2. 要件実現可能性分析

#### 技術要件の抽出
- requirements.mdからEARS形式の要件を解析
- 各要件に必要な技術コンポーネントの特定
- 非機能要件（セキュリティ、パフォーマンスなど）の抽出
- ビジネスロジックの複雑さと統合ポイントのマッピング

#### ギャップの特定
- 要件に対する不足している技術能力
- 調査が必要な未知の技術や外部依存
- 既存システムとの潜在的な統合課題
- リサーチやPoC作業が必要な領域

### 3. 実装アプローチオプション

#### 複数戦略の評価

**Option A**: 既存コンポーネント/ファイルの拡張
- 拡張するファイル/モジュールの特定
- 現在のパターンとの互換性
- コードの複雑さと保守性への影響

**Option B**: 新規コンポーネントの作成（正当化される場合）
- 新規ファイル作成の明確な根拠
- 既存システムとの統合ポイント
- 責任境界とインターフェース

**Option C**: ハイブリッドアプローチ
- 拡張と新規作成の組み合わせ
- 段階的な実装戦略
- リスク軽減アプローチ

### 4. 技術リサーチ要件

#### 外部依存分析（該当する場合）
- 現在使用されていない必要なライブラリ、API、サービス
- 既存依存関係とのバージョン互換性
- 認証、設定、セットアップ要件
- レート制限、使用制約、コストへの影響

#### 知識ギャップ評価
- チームに馴染みのない技術
- リサーチが必要な複雑な統合パターン
- 調査が必要なパフォーマンスやセキュリティの考慮事項
- ベストプラクティスのリサーチ要件

### 5. 実装複雑度評価

#### 工数見積もり
- **Small (S)**: 1-3日、主に既存パターンを使用
- **Medium (M)**: 3-7日、いくつかの新しいパターンや統合
- **Large (L)**: 1-2週間、重要な新機能
- **Extra Large (XL)**: 2週間以上、複雑なアーキテクチャ変更

#### リスク要因
- **High**: 未知の技術、複雑な統合、アーキテクチャ変更
- **Medium**: 新しいパターン、外部依存、パフォーマンス要件
- **Low**: 既存パターンの拡張、よく理解された技術

## 出力形式

### Analysis Summary
- フィーチャースコープと複雑度の概要
- 特定された主要な技術課題
- 全体的な実装アプローチの推奨

### Existing Codebase Insights
- 関連する既存コンポーネントとその現在の責任
- 従うべき確立されたパターンと規約
- 利用可能な再利用可能なユーティリティとサービス

### Implementation Strategy Options
- **Approach**: [Extension/New/Hybrid]
- **Rationale**: このアプローチが適切な理由
- **Trade-offs**: 長所と短所
- **Complexity**: [S/M/L/XL] と根拠

### Technical Research Needs
- 調査が必要な外部依存
- リサーチが必要な未知の技術
- PoC作業が必要な統合パターン
- 調査すべきパフォーマンスやセキュリティの考慮事項

### Recommendations for Design Phase
- 根拠を伴う推奨実装アプローチ
- 行うべき主要なアーキテクチャ決定
- 設計中にさらに調査が必要な領域
- 設計フェーズで対処すべき潜在的リスク

## 使用例

```bash
# 実装ギャップを分析
/kiro:validate-gap user-authentication

# 特定の側面を分析
/kiro:validate-gap user-authentication "database integration"
```

## 次のフェーズ

分析後：
- `/kiro:spec-design <feature-name>` - 技術設計ドキュメントを作成
- `/kiro:spec-design <feature-name> -y` - 要件を自動承認して設計を生成
