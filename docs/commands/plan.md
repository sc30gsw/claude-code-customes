# /plan - 実装計画コマンド

---
description: 要件を再確認し、リスクを評価し、ステップバイステップの実装計画を作成。コードに触れる前にユーザーの確認を待つ。
---

## 概要

`/plan` コマンドは **planner** エージェントを呼び出し、コードを書く前に包括的な実装計画を作成します。

## 機能

1. **要件の再確認** - 何を構築する必要があるかを明確化
2. **リスク特定** - 潜在的な問題とブロッカーを表面化
3. **ステップ計画作成** - 実装をフェーズに分解
4. **確認待機** - 続行前に必ずユーザー承認を受ける

## 使用タイミング

以下の場合に `/plan` を使用:
- 新機能の開始時
- 重要なアーキテクチャ変更時
- 複雑なリファクタリング作業時
- 複数のファイル/コンポーネントに影響する場合
- 要件が不明確または曖昧な場合

## 動作フロー

plannerエージェントは以下を実行:

1. **リクエスト分析** - 要件を明確な言葉で再記述
2. **フェーズ分解** - 具体的で実行可能なステップに分解
3. **依存関係特定** - コンポーネント間の依存関係を特定
4. **リスク評価** - 潜在的なブロッカーを評価
5. **複雑度見積もり** - High/Medium/Lowで評価
6. **計画提示** - 明示的な確認を待つ

## 使用例

```
User: /plan マーケット解決時のリアルタイム通知を追加したい

Agent (planner):
# 実装計画: リアルタイムマーケット解決通知

## 要件の再確認
- ウォッチ中のマーケットが解決した時にユーザーに通知
- 複数の通知チャネルをサポート（アプリ内、メール、webhook）
- 通知が確実に配信されることを保証
- マーケット結果とユーザーのポジション結果を含む

## 実装フェーズ

### Phase 1: データベーススキーマ
- notifications テーブル追加
- user_notification_preferences テーブル追加
- パフォーマンス用インデックス作成

### Phase 2: 通知サービス
- lib/notifications.ts に通知サービス作成
- BullMQ/Redisを使用した通知キュー実装
- 失敗配信のリトライロジック追加
- 通知テンプレート作成

### Phase 3: 統合ポイント
- マーケット解決ロジックにフック
- マーケット内のポジションを持つユーザーをクエリ
- 各ユーザーの通知をキューに追加

### Phase 4: フロントエンドコンポーネント
- ヘッダーにNotificationBellコンポーネント作成
- NotificationListモーダル追加
- Supabaseサブスクリプションでリアルタイム更新
- 通知設定ページ追加

## 依存関係
- Redis（キュー用）
- メールサービス（SendGrid/Resend）
- Supabaseリアルタイムサブスクリプション

## リスク
- HIGH: メール配信性（SPF/DKIM必須）
- MEDIUM: マーケットあたり1000+ユーザーでのパフォーマンス
- MEDIUM: マーケットが頻繁に解決する場合の通知スパム
- LOW: リアルタイムサブスクリプションのオーバーヘッド

## 見積もり複雑度: MEDIUM

**確認待ち**: この計画で進めますか？ (yes/no/modify)
```

## 重要な注意事項

**CRITICAL**: plannerエージェントは、明示的に「yes」や「proceed」などの肯定的な応答で計画を確認するまで、コードを書きません。

変更が必要な場合:
- "modify: [変更内容]"
- "different approach: [代替案]"
- "Phase 2をスキップしてPhase 3を先に"

## 他のコマンドとの連携

計画後:
- `/tdd` でテスト駆動開発で実装
- `/build-fix` でビルドエラー発生時に使用
- `/code-review` で完成した実装をレビュー
