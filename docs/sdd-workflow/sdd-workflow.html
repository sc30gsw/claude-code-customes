SDD ワークフロー — Spec-Driven Development ガイド

対象読者: エンジニア・非エンジニアを問わず、AI アシスタントと協力して Notion のバックログチケットから Pull Request まで一気通貫で進めたい方

1. このワークフローが解決すること

問題定義

状態 問題
Notion Backlog にチケットがある 要件が自然言語で書かれており曖昧。実装者によって解釈が異なる
実装に入った 何を作ったか・なぜこう作ったかの根拠がコードに残らない
レビュー・マージ後 要件とコードの対応関係が失われ、後から追跡できない

SDD ワークフローはこの問題を 9 フェーズ + 厳格な承認ゲート で解決します。 

Notion Backlog
    ↓ /sdd-init
source-notion.md  (Notion の内容をローカル保存)
    ↓ /sdd-requirements
requirements.md   (REQ-001..N — EARS 形式の要件定義)
    ↓ /sdd-design
design.md         (Mermaid 図 + ファイル構造)
    ↓ /sdd-tasks
tasks.md          (TASK-001..M — 実装タスク一覧)
    ↓ /sdd-impl
コード + テスト   (TASK-001 ごとにコミット)
    ↓ /sdd-pr
GitHub PR         (REQ → TASK → commit のトレーサビリティテーブル付き)

3. 各 Skill（コマンド）の説明

SDD は .claude/skills/sdd-*/ に定義されたスキル群です。各スキルはスラッシュコマンドで起動し、 .claude/specs/<slug>/ に成果物を書き込みます。モードは sdd-init で一度だけ決め、 以降は progress.md を参照します。

/sdd-init

フェーズ 1 — Init

機能ごとの spec ディレクトリを初期化します。Notion URL があれば source-notion.md に保存し、progress.md に standard / auto を記録します。常に最初に実行します。

成果物: source-notion.md, progress.md

/sdd-requirements

フェーズ 2 — Requirements

source-notion.md をもとに EARS 形式の requirements.md（REQ-001..N）を作成します。 standard では人間が内容を埋め、AI が補助。auto では質問に答えると AI が要件を組み立てます。

成果物: requirements.md

/sdd-review-requirements

フェーズ 3 — Review Req

要件の曖昧さ・矛盾・受入基準の不足をレビューし、review.md に §Requirements Review を追記します。 ECC requirements-analyst を起動。standard では技術調査（spec-tech-research）も実施します。

成果物: review.md §Requirements Review

/sdd-design

フェーズ 4 — Design

要件をもとに Mermaid 図・ファイル構造・状態管理方針を含む design.md を作成します。 ECC /plan（planner）に委譲し、プロジェクトの設計テンプレートにマージします。

成果物: design.md

/sdd-tasks

フェーズ 5 — Tasks

設計を TDD 順の実装タスク（TASK-001..M）に分解し、各タスクに対応 REQ・設計セクションを紐付けます。 tasks.md と progress.md のタスク一覧を更新します。

成果物: tasks.md, progress.md

/sdd-review-plan

フェーズ 6 — Review Plan

REQ → 設計 → タスクのトレーサビリティを検証し、プランをレビューします。 6 項目の整合性チェックがすべて ✅ のときだけ実装に進めます。§Plan Review と §Traceability Coherence を追記します。

成果物: review.md §Plan Review, §Traceability

/sdd-impl

フェーズ 7 — Implement

タスクごとに ECC tdd-workflow で Red → Green → Refactor を実行し、 feat(TASK-NNN): 形式でコミットします。引数なしで全 pending タスク、TASK-003 で再開も可能です。

成果物: コード・テスト, progress.md

/sdd-review

フェーズ 8 — Code Review

ブランチ差分に対してコードレビューとセキュリティレビューを実行します（Claude Code /code-review、ECC /security-review）。 指摘は自動修正せず review.md に記録。CRITICAL が残っている場合は PR 前に解消します。

成果物: review.md §Code Review, §Security

/sdd-pr

フェーズ 9 — PR

REQ → TASK → commit のトレーサビリティ表とテスト計画を含む GitHub PR を作成します。 実際の PR 作成は git-pr スキルに委譲します。

成果物: GitHub PR

/sdd-workflow

Meta（読み取り専用）

各フェーズの完了状況・次に実行すべきコマンド・ブロッカーを表示します。ファイルは変更しません。 slug 省略時は .claude/specs/ 配下の全機能を一覧表示します。

成果物: なし（ステータス表示のみ）

補助スキル・エージェント（フェーズ内で呼び出し）

上記の sdd-* スキルがオーケストレーターとなり、必要に応じて既存スキル・ECC エージェントを組み合わせます。

スキル / エージェント 使われるフェーズ 役割
spec-tech-research 3, 4, 6（standard のみ） ライブラリ選定・技術的実現可能性の調査
ECC requirements-analyst 3 要件の品質チェック（EARS・曖昧表現・受入基準）
ECC planner / /plan 4, 6（standard の 6 のみ） 設計・タスク分解の作成と検証
ECC architect 6 アーキテクチャ観点のプレビュー
ECC tdd-workflow 7 テスト駆動実装（Red → Green → Refactor）
Claude Code /code-review 8 コード品質・規約準拠のチェック
ECC /security-review 8 セキュリティ観点のチェック
git-pr 9 GitHub PR の作成

4. --mode standard と --mode auto の違い

モードは /sdd-init <slug> [--mode standard|auto] で指定します（省略時は standard）。以降のスキルは progress.md の Mode を読み取り、対話の仕方と呼び出すエージェントが変わります。

standard（デフォルト）

誰が主導: エンジニアが意思決定、AI が補助・レビュー支援

向いている場面: 設計判断や実装の中身を確認しながら進めたい、技術調査結果を自分で評価したい

  • 各フェーズ完了後に CONFIRM で次へ進む
  • TDD の RED / GREEN / REFACTOR ごとに一時停止して確認
  • 要件・プラン・コードレビューで技術調査スキルを併用

auto

誰が主導: AI が草案作成・実装まで進め、人間は重要な承認ポイントで判断

向いている場面: 非エンジニアがバックログから PR まで進めたい、定型的な実装を AI に任せたい

  • 要件定義は質問に答えると AI が EARS 形式で記述
  • 実装中は TDD サイクルを自動で連続実行
  • 承認は要件レビュー・プラン・コードレビューなど重要ゲートに集中
観点 standard auto
想定ユーザー エンジニア 非エンジニア / AI に任せたいエンジニア
主導者 人間が意思決定、AI がサポート AI が主導、人間は承認のみ
要件定義（フェーズ 2） テンプレートを見ながら人間が記述、AI が補助 AI が質問 → 回答をもとに要件を自動生成
要件レビュー（フェーズ 3） analyst + planner + spec-tech-research analyst のみ（ビジネス観点の指摘を優先）
プラン review（フェーズ 6） planner + architect + spec-tech-research architect のみ
実装（フェーズ 7） RED / GREEN / REFACTOR ごとに停止して確認 TDD サイクルを連続実行、タスク完了まで自動ループ
コードレビュー（フェーズ 8） 指摘一覧を提示、修正はエンジニアが判断 CRITICAL / HIGH に修正提案を併記（適用はしない）
承認ゲート 全フェーズで CONFIRM が必要 重要なゲートに集中（フェーズ 3, 6, 8 など）
対話 AI に質問しながら進める AI からの確認事項を最小化

フェーズごとのモード差（要約）

フェーズ standard での動き auto での動き
2 Requirements 人間が REQ を埋める。AI は EARS 整形と不足指摘を支援 7 問のヒアリング後、AI が requirements.md を一括作成
3 Review Req 技術実現性まで含めた多角的レビュー → CONFIRM sdd-design ビジネス・受入基準中心のレビュー → 懸念を平易に説明して承認待ち
7 Implement テスト失敗・実装・リファクタの各段階で人間が確認 タスク単位で自動コミット。チェック失敗時は最大 3 回まで自己修正
8 Code Review エンジニア向けの技術的指摘リスト 重大度の高い指摘に修正案を添えて提示

モードの指定方法

# standard（省略時と同じ）
/sdd-init mail-groups-filter https://www.notion.so/enechange/xxxx

# auto
/sdd-init payment-refactor https://notion.so/... --mode auto

auto では各フェーズを AI が進め、承認ゲートに達したときだけ停止します。例: 

AI: フェーズ 3（要件レビュー）が完了しました。
    以下の点が懸念されます：
    - REQ-003 の受入基準が具体的でない可能性があります

    続行するには CONFIRM sdd-design と入力してください。
    修正が必要な場合は、修正内容を指示してください。
