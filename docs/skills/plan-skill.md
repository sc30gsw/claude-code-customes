# Plan Skill

## 概要

コードを書く前に包括的な実装計画を作成するスキル。要件の再確認、リスク評価、ステップバイステップの実装計画を作成し、ユーザーの承認を待ってから実装を開始します。

## アクティベーショントリガー

- 新機能の実装を開始する時
- 重要なアーキテクチャ変更を行う時
- 複雑なリファクタリングに取り組む時
- 複数のファイル/コンポーネントに影響する時
- 要件が不明確または曖昧な時

## 使用方法

```bash
/plan
```

## このスキルが行うこと

1. **要件の再確認** - 構築すべき内容を明確化
2. **リスクの特定** - 潜在的な問題やブロッカーを洗い出し
3. **ステップ計画の作成** - 実装をフェーズに分解
4. **確認待ち** - 実装前にユーザーの承認を必須とする

## プランナーエージェントの動作

1. **リクエストを分析**し、要件を明確な言葉で再確認
2. **フェーズに分解**し、具体的で実行可能なステップを提示
3. **依存関係を特定**（コンポーネント間の関係）
4. **リスクを評価**し、潜在的なブロッカーを特定
5. **複雑度を見積もり**（High/Medium/Low）
6. **計画を提示**し、明示的な確認を待つ

## 出力例

```markdown
# 実装計画: リアルタイム通知

## 要件の再確認
- マーケット解決時に通知を送信
- 複数チャネルをサポート（アプリ内、メール、Webhook）
- 信頼性の高い配信を確保

## 実装フェーズ

### Phase 1: データベーススキーマ
- 通知テーブルを追加
- ユーザー通知設定テーブルを追加
- パフォーマンス用インデックスを作成

### Phase 2: 通知サービス
- 通知サービスを作成
- 通知キューを実装
- リトライロジックを追加

## リスク
- HIGH: メール配信性
- MEDIUM: 多数のユーザーでのパフォーマンス
- LOW: リアルタイムサブスクリプションのオーバーヘッド

## 推定複雑度: MEDIUM

**確認待ち**: この計画で進めますか？（yes/no/modify）
```

## 重要な注意事項

**クリティカル**: プランナーエージェントは、「yes」または「proceed」で明示的に確認するまで**コードを書きません**。

変更が必要な場合は以下のように回答：
- "modify: [変更内容]"
- "different approach: [代替案]"
- "skip phase 2 and do phase 3 first"

## 他のコマンドとの連携

計画後：
- `/tdd` を使用してテスト駆動開発で実装
- ビルドエラーが発生した場合は `/build-fix` を使用
- 完了した実装をレビューするには `/code-review` を使用

## ベストプラクティス

1. **具体的な要件** - 曖昧さを排除した明確な要件確認
2. **リスク優先** - 高リスク項目を先に対処する計画
3. **段階的実装** - 大きな変更を小さなフェーズに分割
4. **テスト計画含む** - 各フェーズにテスト戦略を含める
5. **ロールバック考慮** - 問題発生時の対応策を含める
